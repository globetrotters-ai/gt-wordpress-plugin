# CLAUDE.md

Contributor guide for this repository, written for humans and for coding agents (Claude Code loads it automatically). Read it before changing code. Internal notes, if you have them, live in an untracked `CLAUDE.local.md` beside this file.

## Commands

```bash
make install           # composer install (dev tooling only — see "Dependency-free by design")
make lint              # PHPCS: WPCS + PHP 7.4 compatibility
make lint-fix          # phpcbf, auto-fix what it can
make test              # PHPUnit unit suite (Brain\Monkey, no WordPress booted)
make check             # lint + test, the gate before pushing
make dist              # build/globetrotters-ai-presence.zip, .distignore applied
make release           # versioned zip + update.json staged into RELEASE_DIR (maintainers)
```

Everything routes through Composer scripts (`lint`, `lint:fix`, `test`); use the Make targets, not the raw tools.

Two targets need Docker + wp-env and boot a real WordPress, so they sit outside `make check`:

```bash
make test-integration  # env:start → integration suite → bin/smoke-routes.sh → env:stop
make plugin-check      # env:start → wp plugin check on the BUILT tree → env:stop
```

`make plugin-check` deliberately checks `build/globetrotters-ai-presence`, not the repo root. wp-env maps the root in as the plugin, and Plugin Check rejects the dev files (`bin/`, `tests/`, `vendor/`, `composer.json`) that `.distignore` strips. Both targets are written as one shell line so `env:stop` always runs, even when `env:start` short-circuits the chain.

CI (`.github/workflows/ci.yml`) has five validating jobs: gitleaks (`.github/workflows/secrets.yml`, called as a reusable workflow: a pinned, checksum-verified binary over the full history of the commit under test, and also run on every branch push and before every release; `.gitleaks.toml` allowlists only the test fixtures' fake tokens, by exact, anchored value), PHPCS on 8.3, the unit suite across PHP 7.4/8.0/8.1/8.2/8.3 (proving the declared `Requires PHP: 7.4` floor), an integration matrix of the WP versions pinned in `ci.yml`'s `wp:` list crossed with a page-cache antagonist (`default` = Wordfence + WP Super Cache, `w3tc` swaps in W3 Total Cache), and Plugin Check. A sixth job, `ci-ok`, is the single required status check: it `needs:` the five and passes only when each (every matrix cell) succeeded or was skipped, so a new validating job must be added to its `needs:` list or it gates nothing. There is no committed `composer.lock`, so each PHP cell resolves its own dev-tool versions. To reproduce one cell locally: `WP_ENV_CORE=WordPress/WordPress#6.8 npm run env:start`.

## Architecture

A WordPress plugin (`globetrotters-ai-presence`) that serves a site's Official AI Presence at its **apex domain**. It pulls the published artefact set from the customer's Globetrotters website URL on a cron cadence, caches it in an option, and serves it. It is the WordPress counterpart of the Globetrotters Symfony bundle (`globetrotters-ai/symfony-bundle`), and the two should stay behaviourally aligned.

The wire formats it consumes and produces (the artefact set, the version marker, the server-log ingest endpoint and its `/ranges` document) are defined by the Globetrotters backend; this repo cites them by contract section, e.g. "ingest contract § Page-view counts (v2)".

Namespace is `Globetrotters\AiPresence\` (PSR-4 from `src/`). `globetrotters-ai-presence.php` is the entry point: plugin header, `const VERSION`, a hand-rolled autoloader, activation/deactivation hooks, and a `plugins_loaded` call into `Plugin::boot()`. `src/Plugin.php` is the composition root and the only place collaborators are constructed.

Module map:

| Directory | Role |
|---|---|
| `src/Serving/` | The request path: `Router`, `HeadInjector`, `LinkHeader`, `Breadcrumbs`, `RobotsFilter`, `ContentTypes`, `PageViewScript`, and the locally generated `Sitemap` and `ApiCatalog` |
| `src/Client/`, `src/Sync/`, `src/Cache/` | Pull artefacts from the website URL, validate, cache, schedule refresh |
| `src/Analytics/` | Agent-traffic reporting: MySQL buffer, flush gate, ingest client; the synced `/ranges` lists (`VendorRanges`, `AiReferrers`, `AiUserAgents`, `PageCacheExclusion`); the optional page-view counter (`PageViewCounter`, `MysqlPageViewStore`) |
| `src/Settings/` | `gtaip_settings` / `gtaip_state` options + the Settings → AI Presence screen |
| `src/Update/` | Self-hosted update checks against the `Update URI` header |
| `src/Admin/` | Admin notices |

### Request lifecycle

`Router` hooks `parse_request` at priority **0** and matches the request path directly against `ContentTypes::MAP`. It does not register rewrite rules. That is what makes it work on managed hosts that funnel everything through `index.php`, and on installs where a security plugin would otherwise intercept `/.well-known/*`. A path miss or a cold cache returns without touching the response, so WordPress handles the request normally.

The same hook answers one write: `POST /.well-known/globetrotters/pv`, the page-view beacon, in its own branch ahead of the `GET`/`HEAD` gate. It is always answered with a bare `204` while the plugin is active, and counted only while page-view counting is on (see "Page-view counts" below).

`HeadInjector` runs on `wp_head` at 20 and prints the homepage JSON-LD. `LinkHeader` runs on `template_redirect` at 11 (beside core's own `rest_output_link_header`) and adds the homepage `Link` header — see the invariant below. `RobotsFilter` extends WordPress's virtual `robots.txt` through the `robots_txt` filter (a physical file would conflict and usually be ignored), at `PHP_INT_MAX` so it reads the file every other filter produced.

The robots.txt block, install profiles and breadcrumb, the served-file set and aliases, the IndexNow key and the sitemap are documented in [`docs/serving.md`](docs/serving.md). Read it before touching `RobotsFilter`, `Breadcrumbs`, `ContentTypes`, `Sitemap` or the key route. The invariants below still apply.

### The `/ranges` document

`Analytics\VendorRanges` pulls `GET <ingest endpoint>/ranges` at most daily, with the ingest token, and stores each list it carries in its **own** non-autoloaded option, so a request path reads only the list it needs and never the vendor IP ranges (two orders of magnitude larger). A `200` replaces every list; a `304` re-stamps every list; a failure touches none. `If-None-Match` is sent only while every companion list is stored at the ranges' version (`VendorRanges::companions_current()`): a `304` can keep a list current but never fill it, so an install upgrading into a new list fetches it on its next sync. Each list is unused past 14 days.

| Member | Store | Read by |
|---|---|---|
| `ranges` | `gtaip_vendor_ranges` (`VendorRanges`) | captured bot requests, to mark `verified` + `vendor` |
| `aiReferrers` | `gtaip_ai_referrers` (`AiReferrers`) | the page-view beacon, only when it carries a hint |
| `cacheExclusionUserAgents` | `gtaip_cache_exclusion` (`PageCacheExclusion`) | the page-cache exclusion sync |
| `aiUserAgents` | `gtaip_ai_user_agents` (`AiUserAgents`) | `/robots.txt` |

### The AI crawler registry

`aiUserAgents` (ingest contract § "AI user-agent registry (v6)") is the list of AI crawlers robots.txt names, in emission order: `[{name, fallbackGroup?}]`, where `fallbackGroup` names the agent whose group this one reads when the site names none of its own (`Applebot` → `Googlebot`). `RobotsFilter` uses it when it is stored, at most 14 days old and non-empty after validation, so a new crawler reaches every reporting install with no plugin release. Otherwise it uses the compiled `RobotsFilter::AI_BOTS` + `FALLBACK_GROUPS`: an offline floor **frozen** at 26 names, no longer updated per crawler, and pinned byte for byte by `tests/fixtures/robots-ai-groups.txt` (never hand-edit it). With no list, a stale one or an unusable one, robots.txt is byte-identical to the floor's output.

Validation (`AiUserAgents::parse()`, applied when stored and again when read, since `wp option update` bypasses the sync): not a JSON list, or more than 64 entries, reads as empty; an entry is kept only when `name`, and `fallbackGroup` if present, match the product-token grammar `^[A-Za-z_-]+$` — an invalid entry is skipped, never repaired. A synced list carries its own fallbacks; the compiled map is not consulted for it. Installs without reporting configured never sync and always use the floor. The Symfony bundle applies the same rules; keep the two in step.

### Page-view counts

Optional and **off by default** (`gtaip_settings['count_page_views']`), active only while reporting is configured (`Options::counts_page_views()`); the wire contract is ingest contract § "Page-view counts (v2)". `Serving\PageViewScript` hooks `wp_footer` (only when on — nothing is hooked otherwise) and prints a <500-byte inline script through `wp_print_inline_script_tag()` that, once the page is actually shown (a Speculation Rules prerender waits for `prerenderingchange`), `sendBeacon`s `{"p": location.pathname}` to the same-origin `/.well-known/globetrotters/pv`, plus `r` (the referrer's host, only when it is another host) and `u` (`utm_source`, left out past 100 characters rather than cut, which could split a surrogate pair). The script is byte-identical to the Symfony bundle's, pinned as a literal in `tests/unit/Serving/PageViewScriptTest` and in the bundle's beacon test; change both together. `Router` answers that POST with a bare `204` (`no-store` on both cache headers, `DONOTCACHEPAGE`) — counting on or off, so cached pages still beaconing after counting is switched off cost no 404 render and trip no security plugin's 404 lockout — and, only while counting is on, hands `Analytics\PageViewCounter` only the `Origin`/`Sec-Fetch-Site`/`Referer`/`User-Agent` strings and a ≤1 KB body: same origin (a real `Origin` host decides; else `Sec-Fetch-Site: same-origin`, which is how a `Referrer-Policy: no-referrer` page's `Origin: null` beacon is counted; else the `Referer` host), the contract's path rules (no `?`/`#`, single leading `/`, ≤512 bytes, trailing slash folded), a coarse bot marker discards (`(?<!cu)bot`, so CUBOT phones count), an AI-browser marker buckets `ai_browser`. For a `browser` view carrying `r` or `u` as strings, `Analytics\AiReferrers` matches them against the synced AI referrer list (`r` in `hosts` first — lower-cased, `:port` and trailing dot stripped — then — only when `r` is empty or none of `searchHosts` — `u` in `utmSources`, trimmed, lower-cased and cut at its first `?`; a host match wins) and only the platform is kept; `r`/`u` are never stored, logged or sent. It increments `{prefix}gtaip_page_views` keyed `(UTC day, bucket, md5(path))` in one `INSERT … ON DUPLICATE KEY UPDATE`, where `bucket` is the stored bucket: `browser` / `ai_browser` when unattributed — byte-identical to 0.8.x, so a day 0.8.x opened keeps counting — and `browser@<platform>` when matched (schema 4 widens the column to `varchar(48)`; before it lands `Schema::page_view_platforms_ready()` is false and referred views count as `none`). Past 2000 distinct paths a day (counted across buckets and platforms) a newly created row is removed and the view goes to the literal `(other)` under its own stored bucket. `Flusher` prunes days older than 7 (the backend's window), seals each closed day's rows with a `wp_generate_uuid4()` assigned once (`WHERE record_id IS NULL`), and sends up to 2000 sealed rows per batch under `pageViews` as `{id, day, path, bucket, platform, count}` (`PageViewCounter::split_stored_bucket()`; a row without a platform is `none`), sharing the halving `fit()` with events — an oversized envelope sheds page views before events, an unencodable one halves events only; rows are deleted only after a 2xx, and a page-view-only envelope (`"events": []`) is valid. The counts are indicative (a same-origin endpoint can be spammed, JS-off visitors are missed); the backend never bills on them.

### The AI referrer list

`aiReferrers: {hosts, utmSources, searchHosts}` (ingest contract § "AI referrals (v4)") is stored by `AiReferrers::replace()` in `gtaip_ai_referrers` (`{version, fetched_at, hosts, utmSources, searchHosts}`, `version` = the ranges document's). `AiReferrers` knows nothing about `VendorRanges`: the sync writes it, not the reverse. A `200` without `aiReferrers` stores empty lists. Missing, unreadable or older than 14 days, the list matches nothing. Entries are kept only with a platform matching `^[a-z0-9_-]{1,32}$`.

`searchHosts` (optional, since 0.11.0) lists the mixed search hosts behind which `utm_source` is never read: a tagged link clicked in Google's results is a search click. A bare pattern matches the normalised host exactly; `<name>.*` matches `<name>.` plus one or two TLD labels of 2+ letters (`google.*` is `google.fr` and `google.co.uk`, never `gemini.google.com`), the backend's own search-host rule; an empty list matches nothing, the empty host included. A document without the key reads as an empty list, so utm_source is read behind every host, as before. A record stored without the key (by 0.10.0 or earlier) still matches, but `AiReferrers::version()` reports `null` for it, so the next sync sends no `If-None-Match` and a `200` brings the key. Mirrors the Symfony bundle's `AiReferrers`.

### The page-cache exclusion

Opt-in and **off by default** (`gtaip_settings['exclude_ai_from_page_cache']`), active only while site capture is (`Options::excludes_ai_from_page_cache()`); the wire contract is ingest contract § "Page-cache exclusion (v5)". `Analytics\PageCacheExclusion` registers the backend's `cacheExclusionUserAgents` (live retrieval and AI search agents, never typed here) as "never cache" in the page cache `CaptureContext::page_cache()` detects, and reports `captureContext.pageCacheExclusion: true` only while it is applied to exactly that cache. Supported: WP Rocket (the `rocket_cache_reject_ua` filter, registered on every request while applied there, then `rocket_generate_config_file()` + `flush_rocket_htaccess()`), W3 Total Cache (`pgcache.reject.ua` through `W3TC\Dispatcher::config()`, then W3TC's own `fix_in_wpadmin` for the disk-enhanced rules) and LiteSpeed Cache (`cache-exc_useragents` through `LiteSpeed\Conf::cls()->update_confs()`, which rewrites its `.htaccess` no-cache rule). **WP Super Cache is deliberately unsupported:** its rejected user agents are read only when deciding whether to *store* a page (`wp_cache_ob_callback`, `wp_cache_phase2`), never in `wp_cache_serve_cache_file`, so a page cached by a human visit is still served to an AI agent. Two non-autoloaded options, one writer each: `gtaip_cache_exclusion` holds the list at the ranges version (written by the ranges sync), and `gtaip_cache_exclusion_applied` what was applied (written by `sync()`): the cache, the entries this plugin *added* (an entry the owner already listed is never recorded, so never removed), the list it was asked for, and `served`, false only when W3TC's Disk: Enhanced rules could not be rewritten (retried on every sync). `is_active()` keys on the list asked for, not the entries added, so an owner who already listed every agent still reports the exclusion. `sync()` runs after the ranges fetch on both ticks (priority 21) and on every settings save (outside `is_admin()`); it re-applies after a list change or a cache swap. `Plugin::deactivate()` calls `remove_all()`, and `uninstall.php` requires the class file by hand to run `remove_recorded_on_uninstall()` before deleting the option. `tests/integration/PageCacheExclusionTest` runs against real W3TC in CI's `w3tc` cell, W3TC's own `_check_ua()` read gate included.

### Scheduled work

| Hook | Owner | Cadence |
|---|---|---|
| `gtaip_refresh` | `Cache\RefreshScheduler` | hourly poll; pulls only when due (`refresh_interval`, default daily) |
| `gtaip_flush` | `Analytics\FlushScheduler` | every 15 minutes |
| `gtaip_flush_now` | `Analytics\FlushScheduler` | one-off, queued when the buffer fills |

Both flush hooks also run `Plugin::ensure_reporting_storage()` at priority 9, before the flush: a schema bump arriving by auto-update reaches an install nobody logs into on its next flush, not only on its next admin page load.

`gtaip_refresh` always recurs hourly, whatever `refresh_interval` says: each run is a poll, and `RefreshScheduler::is_due()` pulls only when nothing is cached, `last_refresh` is `0`, or the interval has elapsed since `last_refresh` (with 5 minutes' slack, since the stamp lands when the previous pull *finishes*). `last_refresh` is stamped only on a fully successful pull, so a failed one is retried on the next poll instead of a day or a week later. `ensure_scheduled()` replaces an event left at any other recurrence. `gtaip_flush_now` is a separate hook rather than a second `gtaip_flush` because `wp_schedule_single_event()` refuses an event whose hook and args already match a scheduled one. `Plugin::activate()` calls each scheduler's `register()` before its `ensure_scheduled()`: `boot()` has not run in the activation request, so without it the flush's custom 15-minute interval is unrecognised when the event is scheduled.

## Invariants worth preserving

- **Stale-serve.** The cached bundle is only ever replaced by a *fully successful* pull. A partial or failed refresh must leave the last known good version serving. Four things count as failure, all guarded by `tests/integration/RefreshStaleServeTest.php`: any required file failing, a JSON artefact that does not parse to an object (JSON-LD: an object or a non-empty list of node objects — a maintenance page answered with `200` passes status and size alike; `llms.txt` is held to no grammar), *every* required file coming back empty at once, and a persist that does not land. `ArtefactCache::store()` returns `bool`, and `ArtefactSync::run()` must not advance `installed_version`/`content_hash` when it is `false`. `update_option()` returns `false` both for a failed write *and* for an unchanged value, so `store()` reads the option back and compares before reporting failure. Stale-serve is **per source**: clearing or changing `website_url` runs `ArtefactSync::forget_previous_source()` — hooked on `update_option_gtaip_settings` outside `is_admin()`, so `wp option update` counts too — and `run()` discards a pull whose destination changed while it was in flight (`Options::still_connected_to()`). `tests/integration/SourceChangeTest` pins it.
- **Every process serves the latest pull, whatever object cache sits in front of the table.** An APCu `object-cache.php` drop-in is per PHP process pool, so a pull from system cron through WP-CLI could write the table while PHP-FPM kept serving its cached bundle. `ArtefactCache::store()` writes the bundle with a fresh `generation`, then `gtaip_artefacts_stamp` (generation, version, `stored_at`, `pulled_by` lane + OS user); a stamp that does not land fails the store and rolls the bundle back. Behind a persistent object cache (`wp_using_ext_object_cache()`), `bundle()` reads the stamp past the cache (evict the key *and* its `notoptions` entry, then `get_option()`) and re-reads any bundle that is not provably current. Without a persistent cache it reads nothing extra. A web-lane read (not `WP_CLI`, not `wp_doing_cron()`) writes the autoloaded heartbeat `gtaip_served` when the version changes and at most hourly otherwise; `CaptureContext` sends it as `servedVersion`. `tests/unit/Cache/ArtefactCacheTest` and `tests/integration/CrossProcessCacheTest` pin it.
- **One refresh at a time, locked in the table.** `ArtefactSync::run()` holds `Sync\MysqlRefreshLock` (`gtaip_refresh_lock`, `<time>:<uuid>`) for the pull: `INSERT IGNORE` to take it, compare-and-swap to reclaim one older than 10 minutes, delete-only-our-token to release. Never `add_option()`: it checks the local cache and writes `INSERT … ON DUPLICATE KEY UPDATE`, so two processes behind different caches would both win. A run that finds it held returns a `busy` `SyncResult`; a run whose lock was reclaimed while it fetched (`still_held()` is checked right before the store) discards its pull. `tests/integration/RefreshLockTest` pins it.
- **`GET` and `HEAD` only on the artefact surface.** `Router::is_read_request()` gates every artefact, key, catalog and sitemap path: answering a write method would fold probing traffic into the fetch counts Presence Analytics reports. The single exception is the page-view beacon, `POST /.well-known/globetrotters/pv`, matched on method *and* exact path in its own branch before the gate. `tests/unit/Serving/RouterPageViewTest` pins both halves.
- **The page-view endpoint knows nothing about who sent the beacon.** It never reads `REMOTE_ADDR` or any forwarding header, never stores the User-Agent (it is matched and dropped), never sets a cookie, and answers the same bare `204` whether it counted or not. The referrer host and `utm_source` hints are matched and dropped the same way. The counter table has no column for visitor data. `RouterPageViewTest::test_the_endpoint_never_reads_an_ip_header` swaps `$_SERVER` for a read-recording spy; extend it, never weaken it.
- **A beacon reads the AI referrer list only when it carries a hint, and never the vendor ranges.** `AiReferrers::match()` returns `none` before any `get_option()` when `r` and `u` normalise to empty, and `ai_browser` views never call it. `AiReferrersTest`, `PageViewCounterTest` and `RouterPageViewTest` record every option read to pin both.
- **`/robots.txt` reads the crawler registry, never the vendor ranges.** `RobotsFilter` reads only `gtaip_ai_user_agents` through `AiUserAgents`; the floor output is byte-identical to the compiled constant's.
- **One artefact, one URL.** `Router::request_path()` resolves only the canonical single-leading-slash form and never collapses or rewrites a requested path. A second leading slash makes `REQUEST_URI` a protocol-relative URL, so `parse_url()` reads the next segment as an *authority*: `//anything/llms.txt` parses to `/llms.txt`. Without the guard every artefact was reachable at unlimited duplicate URLs.
- **`no-store` is a measurement precondition, not an optimisation.** `Router::response_headers()` sets both `Cache-Control: no-store` and `Surrogate-Control: no-store`. A shared TTL in front of the origin means PHP never executes and the reported hit count goes silently low. `Surrogate-Control` is what Cloudflare and Varnish honour.
- **`Access-Control-Allow-Origin: *` is scoped to the artefact paths and the API catalog only.** This is the apex of a site we do not own; never widen it to the rest of the install (the key file and the sitemap stay without it).
- **Dependency-free by design.** The shipped ZIP does not load Composer's autoloader. Composer is dev-only (PHPUnit, PHPCS), and the entry point registers its own PSR-4 autoloader. Do not add a runtime `require vendor/autoload.php` or a runtime Composer dependency.
- **`website_url` is untrusted input, and must be https.** `Client\GtClient` fetches with `reject_unsafe_urls => true` and a 5s timeout; keep any new outbound fetch on that client. What is pulled is published at the customer's apex, so a cleartext pull lets anyone on the path rewrite the site's presence. The sanitizer refuses anything `Options::is_https_url()` rejects, and `ArtefactSync::run()` / `check_latest()` refuse it again before any fetch, because `wp option update` bypasses the sanitizer. `GtClient` follows redirects itself (core is called with `'redirection' => 0`, because its `validate_redirects()` accepts an `http://` `Location`): 301/302/303/307/308 up to 5 hops, each `Location` resolved against the URL that sent it, failing the fetch before requesting any non-https target.
- **The artefact cache option is non-autoloaded.** `gtaip_artefacts` can reach hundreds of KB; autoloading it would land it in `alloptions` on every request and can breach memcached's 1 MB value limit. `update_option( ..., false )` is load-bearing.
- **The buffer and page-view tables survive deactivation, and are dropped only on uninstall.** Readiness is per table: `Schema::is_ready()` (version ≥ 1) gates the event buffer and `Schema::page_views_ready()` (≥ 2) the counters, so a missing counter table leaves page views inert and never stops agent-traffic capture or flushing.
- **`uninstall.php` runs standalone.** No bootstrap, no autoloader, so it hard-codes the table names and every option key. Adding an option or a cron hook means adding it there by hand.
- **The IndexNow key is served only when one is stored, only at its own URL, is matched after the artefact set, is not CORS-readable, and is not agent traffic.** See `docs/serving.md`.
- **The sitemap is generated from the cache, never fetched, and never claims `/sitemap.xml`.** `tests/integration/RouteServingTest` replays every listed `<loc>` back through `Router` to prove the listing and the served set cannot diverge.
- **The API catalog is generated, never fetched, and is agent traffic.** `Serving\ApiCatalog` renders `/.well-known/api-catalog` (RFC 9727) anchored on `Sitemap::site_origin()`, listing only cached targets (`ApiCatalog::RELS`), and is answered exactly when one of them is cached. `LinkHeader` and `Sitemap` apply that rule (`ApiCatalog::is_served_with()`) to the cache reads they already make; change the three together. It gets the artefacts' headers, CORS grant included, and the ingest contract maps it to the `well_known_api_catalog` asset format.
- **`<lastmod>` tracks content, not cron, and never stamps `/`.** `content_changed_at` advances only when `content_hash` changes. `tests/unit/Sync/ArtefactSyncTest` and `tests/unit/Serving/SitemapTest` pin both halves.
- **The homepage `Link` header is added, never replacing, and only on the front page.** `Serving\LinkHeader` mirrors the backend's apex homepage relations (and the Symfony bundle): registered relations first (`api-catalog`, `service-doc`), ours after; `is_front_page()` and not paged, 404, feed or embed; status `200`; the last queued `Content-Type` is `text/html` (or none); only targets this install serves; sent with `header( …, false )` so core's own `Link` header survives. The CLI SAPI keeps no headers, so the suites assert the decision through seams (`status()`, `headers_so_far()`, `send_header()`) and `bin/smoke-routes.sh` asserts both `Link` lines on a real response.
- **Heavy files stay remote.** `llms-full.txt` and `content.md` are linked back to Globetrotters by absolute URL, never served locally. Their absence from `ContentTypes::MAP` is deliberate.
- **`PresenceOrigin::OFFLOADED` is an offload list, not a keep-list.** An artefact nobody has classified must default to *staying local at the apex*, never to being treated as living on a Globetrotters URL.
- **The breadcrumb never degrades to a placeholder.** No derived origin, an origin `esc_url()` rejects, or an origin whose host is this site's own — each emits nothing at all.
- **The plugin adds nothing visible to a customer's pages.** `Breadcrumbs` emits head `<link>` tags only. On `wp_footer` it adds nothing unless page-view counting is switched on; then only `PageViewScript`'s invisible inline script. `tests/integration/BreadcrumbsTest` and `tests/integration/PageViewScriptTest` pin it.
- **robots.txt decoration is policy-neutral by default.** A named agent's group is never added, and every other agent inherits the wildcard rules. `allow_all` and `ai-train` are the customer's opt-ins, never defaults. See `docs/serving.md`.
- **`HeadInjector`'s `EscapeOutput` exemption does not transfer.** It is justified by `render()` producing a breakout-safe `<script>`: `JSON_HEX_TAG`, so the payload carries no `<` or `>` at all. `Breadcrumbs` prints `<link>` tags and puts every URL through `esc_url()`.
- **The ingest endpoint is https-only and never followed through a redirect.** It receives the bearer token and every captured client IP. `Options::ingest_endpoint()` reads anything but `https://` as unconfigured, `IngestClient::post()` refuses one before sending, and `'redirection' => 0` because core's HTTP client re-sends every original header, `Authorization` included, to whatever `Location` a 3xx names. The `/ranges` fetch follows the same rule.
- **Runtime state has one writer per option.** `gtaip_state` belongs to the sync and `gtaip_flush_state` to the flusher (under its lock); each `/ranges` list to the ranges sync. The drop counters are two non-autoloaded option rows that `MysqlEventStore` changes with single statements — created with `INSERT IGNORE`, never `add_option()`. `Options::update_state()` evicts the cached row before merging. `tests/integration/StateConcurrencyTest` pins both.
- **Forwarding headers are evidence only from a listed proxy.** `ClientIp` trusts nothing unless `REMOTE_ADDR` is in `TrustedProxies`. `X-Forwarded-For` is walked from the right past listed hops, and `CF-Connecting-IP` is read only from Cloudflare's own ranges under the preset. `TrustedProxies::CLOUDFLARE` is hand-copied from cloudflare.com/ips; a stale copy fails safe, as an unverified hit.
- **An update offer must carry `version`.** `wp_update_plugins()` skips any `update_plugins_{hostname}` response without it. `tests/integration/UpdateCheckTest` runs core's real update check.
